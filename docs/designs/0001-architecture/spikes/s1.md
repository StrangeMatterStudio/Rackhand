# Spike S1: aya eBPF

**Question (design 17, S1):** do aya programs capture TCP connects, UDP sends and execs on kernels 5.10, 6.1 and the
current Proxmox series, with the pid, the executable path and the cgroup id resolved in the program; what map memory
do they need; does a host-side program attribute a container's connections to the container by cgroup; and which
licence must the program declare for the helpers it uses?

**Answer:** yes on all three kernels, about 0.5 to 1 MB of map memory, and LXC attribution works from the host. The
program must declare a GPL-compatible licence: the kernel refuses `bpf_probe_read_kernel` (a GPL-only helper) from a
program that declares `MIT`. The spike declared `Dual MIT/GPL`, which the kernel accepts. The project's licence for
the eBPF program is the owner's decision before T68.

## Method

An aya 0.16 (aya-ebpf 0.3) program with three hooks, attached to the root cgroup and a tracepoint:
- `cgroup_sock_addr` `connect4` and `sendmsg4` for TCP connects and UDP sends (destination, pid, uid, comm, cgroup id);
- the `sched:sched_process_exec` tracepoint, which records each new process's executable path in an LRU map keyed by
  pid, so the connect and send hooks read the path inside the program;
- a perf ring for events to user space, which maps cgroup ids (cgroup v2 directory inodes) to paths.

On each kernel the eBPF tier's VM ran the program as root, then made a TCP connect to `127.0.0.1:9`, a UDP send to
`127.0.0.1:5353` and an exec of a copy of `/bin/true` from `/tmp`. Map memory is the sum of `memlock` over the
program's map fds. The same program was then built declaring `MIT` and loaded again. For the LXC part, the program ran
on the lab's `pve9` node (Proxmox VE 9.2, kernel 7.0.14-30-pve, nested KVM) while `pct exec` made the unprivileged
container `ct-test` (VMID 100) connect to the hub's SSH port on site A.

## Results

| Kernel | Loaded | TCP connect | UDP | Exec from /tmp | Exe path in program | cgroup id | Map memory |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 5.10.274 | yes | yes | yes | yes | yes | yes | 1080 KB |
| 6.1.192 | yes | yes | yes | yes | yes | yes | 548 KB |
| 7.0.14 | yes | yes | yes | yes | yes | yes | 1070 KB |

- **LXC attribution (pve9):** the container's `nc` connect was reported with cgroup
  `/sys/fs/cgroup/lxc/100/ns/.lxc`, so a host-side program attributes container traffic by the `/lxc/<vmid>/` prefix.
  Processes started with `pct exec` sit in `ns/.lxc`; the container's own processes sit elsewhere under `/lxc/<vmid>/`.
- **Licence:** with `MIT`, loading fails in the verifier: "cannot call GPL-restricted function from non-GPL
  compatible program" at the first `bpf_probe_read_kernel`. Reading the exec filename needs that helper.

## Consequences

- T68 uses these hooks. Container attribution is by the cgroup path prefix (`/lxc/<vmid>/` on Proxmox, the runtime's
  scope for Docker and Podman).
- The eBPF program can't be MIT-only. Options for the owner: the program in its own crate under `GPL-2.0 OR MIT`
  (the rest of the project stays as it is), or reading the exec path without GPL-only helpers (user space reads
  `/proc/<pid>/exe` at event time, which is racy for short-lived processes). Decide before T68.
- MV2 repeats the LXC part on a real Proxmox host in L9.
