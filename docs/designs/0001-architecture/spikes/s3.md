# Spike S3: iroh path detection

**Question (design 17, S3):** how does an iroh connection report a direct versus a relayed path, and how does a sender
wait for a direct path (7.3.11: bulk transfers use direct paths only; E29)?

**Answer (iroh 1.5.0):**
- `Connection::paths()` returns a snapshot of the open paths. Each path reports `is_ip()` (direct), `is_relay()` and
  `is_selected()` (carrying application data). `Connection::paths_stream()` yields a fresh snapshot whenever the
  open or selected paths change.
- `wait_direct(timeout)` watches that stream until a selected path is direct; it either returns how long that took or
  times out cleanly.
- A connection always starts on the relay path and moves to a direct path when hole punching succeeds.

## Method

The spike ran as root in the network tier VM (kernel 6.1.192) with `cargo xtask ci net --spike s3`. The topology was:
- a public segment, `203.0.113.0/24`, with an iroh relay (HTTPS, plus QUIC address discovery on UDP 7842) and two NAT
  routers on it;
- peer `a` behind `nat-a` and peer `b` behind `nat-b`, with nftables `masquerade` on each NAT's public side.

`b` listened. `a` dialed `b` by endpoint id with only the relay address, then ran `wait_direct`. Both peers learned
their public mapping through the relay (for example `203.0.113.11:56538` for `a`).

## Results

| Case | Connected (ms) | Direct | Time to direct, or timeout (ms) | Paths after |
| --- | --- | --- | --- | --- |
| No NAT (both peers on the public segment) | 1 | yes | 0 | relay, and IP `203.0.113.22` selected |
| Both peers behind Linux masquerade | 1 | no | timeout at 30 000 | relay selected |
| Both behind masquerade, with the dialer given the listener's addresses | 1 | no | timeout at 30 000 | relay selected |
| Listener behind full-cone NAT (a static UDP forward of its port), dialer behind masquerade | 1 | yes | 1 | relay, and IP `203.0.113.12:40000` selected |
| UDP blocked at the listener's NAT | 1 | no | timeout at 15 000 | relay selected |

## Consequences

- **Path detection:** the hub's transfer code uses `wait_direct` before sending bulk data, and the dashboard shows
  "direct" or "relay" from `paths()`. E29 ("waits; info event after 10 minutes") can be built as designed.
- **Network tier:** two Linux masquerade NATs don't hole punch. An early punch packet creates a conntrack entry on the
  far NAT, so masquerade picks a new source port, which acts like a symmetric NAT. The T83 test
  `full_cone_connects_direct` therefore builds full cone as this spike did: a static UDP forward of the listener's port.
  The symmetric case is plain masquerade on both sides.
- **For users:** two hubs behind typical Linux-based NATs may stay on the relay. Without a port forward (or UPnP or
  NAT-PMP, which iroh's `portmapper` feature can use), bulk transfers wait (E29). The relay guide should say so. This
  doesn't contradict the design.
