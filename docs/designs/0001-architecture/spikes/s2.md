# Spike S2: iroh relay admission and limits

**Question (design 17, S2):** with the iroh relay embedded in `rackhand relay`, can it admit by key, limit per
endpoint, prioritize keyed endpoints at capacity, and which ports does it need?

**Answer (iroh-relay 1.5.0):** admission by key, a rate limit and priority at capacity work. Per-key rates and daily
quotas are **not possible** with iroh-relay's public API. That contradicts 7.3.10's per-key `--rate` and `--daily` and
the unkeyed 2 GB per day, so it is a design question for the owner (below).

## Method

Run as root in the network tier VM (kernel 6.1.192) with `cargo xtask ci net --spike s2`, on loopback. Relays ran
in-process with an `AccessControl` hook. Clients were iroh 1.5 endpoints with IP transports cleared, so every byte went
through the relay. A relay key was a token `<class>.<name>.<signature>` made with the relay's secret, which the client
sends with `RelayConfig::with_auth_token` (an `Authorization: Bearer` header on the relay connection).

## Results

| Question | Answer | Measured |
| --- | --- | --- |
| Admission with keys (`private` mode) | works | two keyed endpoints came online and relayed 64 KB to each other; an unkeyed endpoint and one with a forged token were refused and never came online |
| Rate limit | works, server-wide only | 1 MB relayed in 8.4 s (119 KB/s) with `Limits::client_rx` at 125 000 B/s (1 Mbit/s); 0.01 s without a limit |
| Per-key rate | not possible | `Limits::client_rx` and `RelayService::set_client_rate_limit` apply one limit to every connection; there is no per-endpoint setting |
| Daily quota | not possible | the server has no per-endpoint byte counters, only server-wide `bytes_recv` and `bytes_sent` metrics |
| Priority at capacity | works | capacity 5 filled with 5 unkeyed endpoints; a `normal` key and then a `high` key were each admitted by evicting an unkeyed endpoint (`Clients::disconnect`); a later unkeyed endpoint was refused; the 5 admitted were 3 unkeyed, 1 normal, 1 high |
| Ports | see below | TCP for HTTP (also the captive-portal probe) and HTTPS, UDP for QUIC address discovery |

**Ports.** Defaults: HTTP 80, HTTPS 443, QUIC address discovery UDP 7842, and optional metrics on 9090. 7.3.10's "HTTPS
on 443 and the QUIC discovery port" is right. Port 80 is also needed for the captive-portal probe and for ACME HTTP-01.

**How the hook works.** `AccessControl::on_connect` receives the client's endpoint id, which the relay handshake has
already authenticated, and its bearer token. It returns allow or deny with a reason. `on_disconnect` is called once for
every admitted connection, so the hook can count connections per class. The hook can reach `Clients::disconnect`
through the server's `RelayService`, which is how a keyed endpoint takes an unkeyed endpoint's place at capacity.

## Design question for the owner

7.3.10 gives each relay key its own `--rate` and `--daily`, and unkeyed endpoints 1 Mbit/s and 2 GB per day.
iroh-relay can't do either per endpoint. Options:

1. **(Recommended)** One rate per relay, set by the operator (default 1 Mbit/s in `public` mode, none in `private`
   mode). Drop the per-key `--rate` and `--daily` and the daily quota. Keys keep admission, priority, `--max-endpoints`
   and `--expires`. No fork of iroh-relay.
2. Two relay listeners in one process, one for keyed endpoints and one for unkeyed, each with its own server-wide rate.
   That gives a rate per class (keyed or unkeyed) but still no daily quota.
3. Patch iroh-relay (a maintained fork) with a per-connection rate hook and byte counters. Keeps the design as written,
   at the cost of carrying the patch through every iroh upgrade.

Until the owner decides, T82 (relay) waits; nothing before it depends on the answer.
